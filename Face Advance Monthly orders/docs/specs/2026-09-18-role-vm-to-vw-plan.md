# แผนเปลี่ยนชื่อ role `Vm` → `Vw` ทั้งระบบ

> สั่งโดยเจ้านาย 2026-09-18 · **ยังไม่ลงมือ — เอกสารนี้คือแผน รออนุมัติ**
> ขอบเขต: เปลี่ยน **ชื่อ** เท่านั้น สิทธิ์และพฤติกรรมทุกอย่างคงเดิม

---

## 🔴 กับดักใหญ่ที่สุด — ลำดับ deploy ผิด = ล็อกเอาต์บัญชีจริง

`frontend/src/pages.ts`

```ts
/** ไม่รู้จัก role → ปลอดภัยไว้ก่อน = ไม่มีหน้า */
export function pagesFor(role: string): PageKey[] {
  const allowed = new Set(ROLE_PAGES[role] ?? []);   // ← 'Vw' ไม่มีใน map = Set ว่าง
  return PAGES.filter((p) => allowed.has(p.key)).map((p) => p.key);
}
```

**ถ้าแก้ DB ก่อน** → บัญชี `plug` จะมี `role='Vw'` แต่บันเดิลเก่ายังรู้จักแค่ `'Vm'`
→ `pagesFor('Vw')` = `[]` → **เข้าระบบได้แต่ไม่มีหน้าให้เปิดเลย · Dock ว่าง** (ไม่ใช่ error ด้วย จะงงว่าพังตรงไหน)

`canEdit('Vw')` = `false` (ค่า fallback) ซึ่งบังเอิญถูก แต่ช่วยไม่ได้เพราะเข้าหน้าไม่ได้ตั้งแต่แรก

### ✅ ลำดับที่ถูก — 3 ก้าว

| ก้าว | ทำอะไร | ระหว่างนี้ระบบเป็นยังไง |
|---|---|---|
| **1** | **Frontend รับทั้ง 2 ชื่อ** (`Vm` และ `Vw` ชี้สิทธิ์เดียวกัน) → deploy | `plug` ยังเป็น `Vm` ใช้งานปกติ · ถ้าเปลี่ยนเป็น `Vw` ก็ใช้ได้ทันที |
| **2** | **DB เปลี่ยนชื่อ** (constraint + ข้อมูล + 6 ฟังก์ชัน) ใน 1 transaction | `plug` เป็น `Vw` · บันเดิลที่ deploy ไว้รับอยู่แล้ว → ไม่สะดุด |
| **3** | **ถอด `Vm` ออกจาก frontend** (เหลือ `Vw` เดียว) → deploy | ปิดงาน |

> ก้าว 3 ไม่รีบ ทำวันหลังได้ · ถ้าข้าม ระบบก็ยังทำงานถูก แค่มีโค้ดค้างที่ไม่ถูกใช้

## 📋 รายการที่ต้องแก้ทั้งหมด (สำรวจแล้วจากของจริง)

### 1. Database — 1 constraint + 1 แถวข้อมูล + 6 ฟังก์ชัน

**constraint**
```
app_users_role_chk  CHECK (role = ANY (ARRAY['OM','RT+','RTs','Adm','Vm']))
```

**ข้อมูล** — `app_users` มี role `Vm` อยู่ **1 บัญชี: `plug`**
*(Adm 1 · OM 1 · RT+ 2 · RTs 5 · Vm 1 = 10 บัญชี)*

**ฟังก์ชันที่มีสตริง `'Vm'`** (นับจาก `pg_get_functiondef`)

| ฟังก์ชัน | จำนวนจุด | ใช้ทำอะไร |
|---|:--:|---|
| `app_can_page` | 1 | เกตสิทธิ์เข้าหน้า |
| `app_returns_list` | 2 | สิทธิ์เห็นทุกทีมในหน้าออเดอร์ตีกลับ |
| `app_returns_stats` | 1 | สิทธิ์เห็นทุกทีมในตัวเลขสรุป |
| `app_search_orders` | 2 | สิทธิ์เห็นทุกทีมในหน้าค้นหา |
| `app_admin_create_user` | 1 | ลิสต์ role ที่สร้างได้ |
| `app_admin_update_user` | 1 | ลิสต์ role ที่แก้เป็นได้ |

**ไม่ต้องแก้:** ไม่มี RLS policy ที่อ้าง `Vm` (เช็คแล้ว `pg_policies` = 0 แถว) · `audit_log` ไม่มี `Vm` เก็บไว้ (0 แถว) · `role` มีอยู่ตารางเดียวคือ `app_users`

## 🧪 เทสที่ต้องผ่านก่อนบอกว่าเสร็จ

**ก่อนแก้ DB** — บันทึกสภาพเดิมไว้เทียบ
```sql
create table _bak_role_vw_20260918 as
  select id, username, role from public.app_users;
```

**หลังก้าว 1 (frontend รับ 2 ชื่อ · ยังไม่แก้ DB)**
- [ ] `plug` (`Vm`) เข้าระบบ เห็น 3 หน้าเดิม: ออเดอร์ · ออเดอร์ตีกลับ · ค้นหา
- [ ] ดินสอแก้ถูกซ่อน (`body.noedit`) · คอลัมน์ "อัพเดต" หาย
- [ ] หน้าจัดการผู้ใช้: badge `Vm` มีสีเหมือนเดิม

**หลังก้าว 2 (DB เป็น `Vw`)**
- [ ] `plug` **ล็อกอินใหม่** แล้วยังเห็น 3 หน้าเดิมครบ *(ต้องล็อกอินใหม่จริง เพราะ role ถูก cache ใน localStorage `fa_role`)*
- [ ] แก้ข้อมูลยังถูกบล็อก (ทั้งฝั่ง UI และฝั่ง server — ลองยิง `app_save_order_tracking` ตรงๆ ต้องถูกปฏิเสธ)
- [ ] หน้าค้นหา + หน้าออเดอร์ตีกลับ: ยังเห็น**ทุกทีม** (ไม่ใช่ทีมเดียว)
- [ ] หน้าจัดการผู้ใช้: badge เป็น `Vw` มีสี · dropdown เลือก role มี `Vw` ไม่มี `Vm`
- [ ] สร้างบัญชีใหม่ role `Vw` ได้ · แก้บัญชีเป็น `Vw` ได้
- [ ] `select * from app_users where role='Vm'` ต้องได้ **0 แถว**
- [ ] role อื่นไม่กระทบ: Adm 5 หน้า · OM 2 หน้า · RT+ 3 หน้า · RTs 2 หน้า

**rollback ถ้าพลาด** — ก้าว 2 อยู่ใน transaction เดียว ถ้า verify ไม่ผ่านให้ `rollback` ทันที · ถ้า commit ไปแล้วค่อยกลับด้วย `_bak_role_vw_20260918` + คืน constraint เดิม
